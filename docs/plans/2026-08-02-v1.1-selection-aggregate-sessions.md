# Daily Ledger v1.1 Selection and Aggregate Sessions Implementation Plan

> **For Hermes:** Implement this plan checkpoint-by-checkpoint with TDD. Freeze and validate each checkpoint before beginning the next one.

**Goal:** Add exact session navigation, durable batch summary generation, manually defined aggregate/Super Sessions, and an optional auto-titled-session visibility filter without breaking v1.0 artifacts or rollback.

**Architecture:** Preserve every v1.0 API and artifact contract. Add profile-scoped session links in the frontend, a durable server-side batch coordinator that invokes the existing per-session pipeline sequentially, and a separate aggregate pipeline/storage family that summarizes selected-day raw transcript slices as one logical session. Keep the visibility preference browser-local so hiding rows never changes canonical inventory or roll-up coverage.

**Tech stack:** Plain JavaScript React IIFE using the Hermes Dashboard Plugin SDK, FastAPI/Pydantic, Python 3.11 standard library, read-only SQLite, pytest, Node test runner, Bash lifecycle scripts.

---

## Accepted Product Locks

1. Aggregates are manually created from checked sessions. Matching titles may suggest a title but never cause automatic grouping.
2. Aggregates contain only the selected calendar day's active message slices.
3. Aggregate generation creates one aggregate artifact and does not automatically create child summaries.
4. Existing per-session summaries, roll-ups, APIs, and artifacts remain readable and backward compatible.
5. Every standalone feature is a checkpoint: write a failing test, implement, run focused tests, run the complete release gate, inspect the diff, commit, and stop before the next feature.
6. No live plugin install or Dashboard restart occurs during implementation. Live acceptance remains operator-controlled after all source gates pass.

## Checkpoint 2: Selection UI and Durable Batch Summaries

**Objective:** Replace per-card generation buttons with checkboxes and a shared toolbar that runs the unchanged per-session summarizer through a durable, bounded server-side batch coordinator.

**Files:**
- Create: `dashboard/hermes_daily_ledger/batch_jobs.py`
- Modify: `dashboard/plugin_api.py`
- Modify: `dashboard/dist/index.js`
- Modify: `dashboard/dist/style.css`
- Create: `tests/test_batch_jobs.py`
- Create: `tests/test_batch_api.py`
- Modify: `tests/test_frontend.js`
- Modify: `tests/test_frontend_runtime.js`
- Modify: `tests/test_live_loader_contract.py`

### Backend contract

1. Add validated request models:
   - member: `profile`, `session_id`;
   - batch request: non-empty distinct members plus `regenerate_current: bool = False`;
   - hard input bound to prevent unbounded request bodies.
2. Canonicalize every requested identity against `build_day_inventory(date)` before reserving work. Reject the whole request before publication if any identity is malformed, duplicated, or absent from the selected day.
3. Persist batch jobs outside plugin code under:

   ```text
   $HERMES_HOME/daily-ledger/batch-jobs/<date>/<batch-id>.json
   ```

4. Store batch state atomically with:
   - immutable batch ID, date, creation/start/finish timestamps;
   - ordered canonical members;
   - overall status `queued|running|completed|partial|failed`;
   - progress counts and current identity;
   - per-item status `queued|running|completed|failed|skipped_current|skipped_running`;
   - sanitized per-item errors and produced version IDs.
5. Add `POST /session-summary/batch?date=YYYY-MM-DD` returning `202` and the durable batch ID.
6. Add `GET /session-summary/batch?date=...&batch_id=...` for exact status.
7. Add `GET /session-summary/batches?date=...` returning bounded metadata so a refreshed page can discover and resume polling an active/recent batch without browser-owned job truth.
8. Run one coordinator thread per batch. Process eligible sessions sequentially through `generate_session_summary`; this is intentionally conservative for a shared local inference route. Do not fire one frontend POST per session.
9. Eligibility rules:
   - missing summary: generate;
   - stale summary: regenerate and retain immutable history;
   - current summary: `skipped_current` unless `regenerate_current=true`;
   - already-running individual job: `skipped_running` rather than aborting the batch.
10. Continue after individual failures. Overall state is `partial` when at least one item completes and at least one fails; `failed` when no eligible item completes.
11. Extend startup recovery to mark interrupted queued/running batch jobs failed. Never infer that their detached inference work continued.
12. Keep existing single-session API routes operational for backward compatibility.

### Frontend contract

1. Add checkbox state keyed by the existing `(date, profile, session_id)` key.
2. Clear selection when the selected date changes or a selected session disappears.
3. Remove per-card generation buttons while retaining summary status, stale state, errors, immutable versions, and restore controls.
4. Insert a toolbar between the selected date/calendar area and the session list:
   - `Generate Selected Summaries (N)` handles missing/stale and skips current;
   - `Regenerate Current Summaries (N)` appears only when selected current summaries exist;
   - `Clear Selection` appears when selection is non-empty.
5. Submit exactly one batch request. Poll exactly one durable batch status with bounded recursive `setTimeout`, never overlapping requests.
6. Reflect per-item queued/running/completed/failed state on child cards. Reload the day and artifacts after terminal batch state.
7. On page reload, query recent batch metadata and resume polling a running batch for that date.

### Tests and snapshot

1. Write RED tests for atomic persistence, status transitions, recovery, duplicate/invalid identities, current-summary skipping, stale regeneration, continuation after failure, bounded listing, and no raw content in status files/API responses.
2. Write API tests with inert fake threads; no test may launch real auxiliary inference.
3. Write frontend tests for selection, shared controls, date-change clearing, one batch POST, one poll in flight, reload recovery, and removal of per-card generation controls.
4. Run focused tests under the project interpreter and Node:

   ```bash
   PYTHONPATH=dashboard python -m pytest tests/test_batch_jobs.py tests/test_batch_api.py tests/test_summary_api.py -q
   node --test tests/test_frontend.js tests/test_frontend_runtime.js
   ```

5. Run the complete network-blocked release gate and diff checks:

   ```bash
   ./scripts/run-tests.sh
   git diff --check
   ```

6. Inspect all changes, commit `feat: add durable batch session summaries`, record snapshot 2 SHA, and stop.

**Acceptance:** Batch progress survives refresh/restart classification; each output remains an ordinary independent session artifact; one failure does not terminate the rest; no browser firehose.

## Checkpoint 3: Aggregate Artifacts and Super Sessions

**Objective:** Generate one independent aggregate summary from selected-day raw slices and render its exact member sessions as a collapsible Super Session.

**Files:**
- Create: `dashboard/hermes_daily_ledger/aggregate_storage.py`
- Create: `dashboard/hermes_daily_ledger/aggregate_jobs.py`
- Create: `dashboard/hermes_daily_ledger/aggregate_orchestrator.py`
- Modify: `dashboard/hermes_daily_ledger/transcript.py`
- Modify: `dashboard/hermes_daily_ledger/chunker.py` only if a reusable lossless seam is required
- Modify: `dashboard/plugin_api.py`
- Modify: `dashboard/dist/index.js`
- Modify: `dashboard/dist/style.css`
- Create: `tests/test_aggregate_storage.py`
- Create: `tests/test_aggregate_jobs.py`
- Create: `tests/test_aggregate_orchestrator.py`
- Create: `tests/test_aggregate_api.py`
- Modify: `tests/test_frontend.js`
- Modify: `tests/test_frontend_runtime.js`
- Modify: `tests/test_live_loader_contract.py`

### Identity, ordering, and storage

1. Request body contains an editable aggregate title, at least two distinct member identities, and explicit `force_regenerate`.
2. Resolve members against the selected day's canonical inventory and selected-day Chicago window.
3. Derive canonical member order from first selected-day message timestamp, with `(profile, session_id)` as deterministic tie-breakers. Preserve message order within each session; where message timestamps are available, globally stable ordering uses timestamp plus source identity and message row ID.
4. Derive a path-safe deterministic aggregate ID from the selected date plus the canonical ordered member identities. Title changes do not change identity.
5. Store under additive roots:

   ```text
   $HERMES_HOME/daily-ledger/aggregate-summaries/<date>/<aggregate-id>/
   $HERMES_HOME/daily-ledger/aggregate-versions/<date>/<aggregate-id>/
   $HERMES_HOME/daily-ledger/aggregate-jobs/<date>/<aggregate-id>.json
   ```

6. Aggregate metadata contains:
   - aggregate ID/title/date;
   - exact ordered canonical member identities and original titles;
   - each member's generation-time source fingerprint;
   - combined deterministic source fingerprint;
   - collection cutoff, model route/model, segment count/method, timestamps, and immutable version ID.
7. Combined fingerprint hashes date plus ordered `(profile, session_id, source_fingerprint)` tuples. Raw message content never appears in metadata.
8. Aggregate staleness is true if a stored member is missing from the day or any current member source fingerprint differs. A different requested member set derives a different aggregate ID rather than silently overwriting another group.

### Generation

1. Collect active `user|assistant|tool` messages directly from each selected session for the selected-day window. Never use saved child summaries as aggregate input.
2. Exclude system prompts, reasoning fields, inactive messages, and plugin-internal sessions exactly as v1.0 does.
3. Treat the selected transcripts as one logical session while retaining server-owned source boundaries in the untrusted-data envelope.
4. Feed the ordered transcripts through the existing lossless safe-ceiling chunking seam. Do not concatenate an unbounded prompt.
5. Every segment returns the existing content-only shape `{summary, key_points}`. Validate and sanitize each segment.
6. Reduce multiple validated segment summaries into one validated aggregate result. Provider-enforced JSON and the existing bounded terminal-closer repair remain in force.
7. Rebuild inventory/fingerprints immediately before atomic publication. If any selected source changed during generation, fail closed and publish nothing.
8. Persist durable aggregate job state `queued|running|completed|failed`; startup marks interrupted work failed.

### API and frontend

1. Add `POST /aggregate-summary?date=...` to create/regenerate.
2. Add `GET /aggregate-summary?date=...&aggregate_id=...` for exact detail/status/history.
3. Add `GET /aggregate-summaries?date=...` returning bounded current aggregate metadata and members for day rendering.
4. Add rollback for immutable aggregate versions using the existing safe version-ID rules.
5. Enable `Generate Aggregate Summary (N)` only when at least two sessions are selected.
6. Suggest an editable title client-side:
   - exact shared title wins;
   - otherwise strip conservative trailing sequence suffixes such as `Part 1`, `- 2`, or `3 of 7` only when every selected title normalizes to the same non-empty base;
   - otherwise fall back to `Aggregate summary for <date>`.
7. On completion, render one collapsed Super Session at the position of its earliest member and remove its children from the ungrouped top-level list.
8. Expanded Super Session shows aggregate status/summary/version history and each original child card with exact link, metadata, independent summary, and restore history.
9. Existing daily roll-up coverage remains based on canonical active sessions and current per-session summaries; aggregate artifacts do not count as child summaries and are never injected automatically.

### Tests and snapshot

1. RED tests cover canonical ordering, selected-day slicing, cross-profile identities, raw-transcript input, no child-summary input, lossless chunk reconstruction, prompt bounds, output validation, fingerprint/staleness, source-change-during-generation failure, immutable versions, rollback, and recovery.
2. API tests use inert worker fakes and prohibit external sockets.
3. Frontend tests cover title suggestion, aggregate request, polling, collapsible rendering, child links, independent child summaries, and no duplicate top-level children.
4. Run focused tests, then full release gate:

   ```bash
   PYTHONPATH=dashboard python -m pytest tests/test_aggregate_storage.py tests/test_aggregate_jobs.py tests/test_aggregate_orchestrator.py tests/test_aggregate_api.py -q
   node --test tests/test_frontend.js tests/test_frontend_runtime.js tests/test_frontend_security.js
   ./scripts/run-tests.sh
   git diff --check
   ```

5. Inspect all changes, commit `feat: add aggregate Super Session summaries`, record snapshot 3 SHA, and stop.

**Acceptance:** One immutable aggregate result represents exact selected-day raw slices; children remain independently identifiable; no oversized prompt; no summary or roll-up contract is repurposed.

## Checkpoint 4: Auto-Titled Session Visibility Toggle

### Steps

1. Add a pure anchored classifier for titles matching only:

   ```text
   Session YYYYMMDD_HHMMSS_<identifier>
   ```

   Do not classify by source alone; meaningfully titled automation remains visible.
2. Add `showAutoTitled` frontend state, default `true`.
3. Persist only the boolean under a namespaced browser-local key. Catch unavailable/corrupt storage and fall back to `true`.
4. Filter only rendered ungrouped session rows and selectable rows. Do not change `/day`, `/month`, roll-up coverage, aggregate metadata, or backend settings.
5. When toggled off, remove newly hidden sessions from selection.
6. Render `X shown · Y auto-titled hidden` so calendar/header counts remain explainable.
7. Super Sessions remain visible. Expanded member rows obey the visibility toggle and report any hidden child count.
8. Write tests for exact matches, near misses, persisted reload, corrupt storage fallback, selection removal, unchanged API data/counts, and aggregate behavior.
9. Run focused frontend tests, full release gate, and diff checks.
10. Commit `feat: toggle auto-titled calendar sessions`, record snapshot 4 SHA, and stop.

**Acceptance:** Default UI matches v1.0; hiding is reversible and local; canonical counts and generation inputs never change implicitly.
